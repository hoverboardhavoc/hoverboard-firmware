1. Repo layout, and runtime-hal

The repository holds four Cargo workspaces, one per build chain: motorcontroller (the GD32 firmware), shared (the crates more than one chain links), tools (the host programs) and bridge (the ESP32-C3 image). Run cargo from inside the workspace; the root holds none.

The firmware depends on the HAL repo as a git dependency: motorcontroller\Cargo.toml names https://github.com/hoverboardhavoc/runtime-hal, and motorcontroller\Cargo.lock pins the commit. Cargo fetches it on the first build (it is public, so no credentials are needed), which also clones its third_party/GD32Firmware submodule, about 23 MB, once. One clone is enough:

cd C:\dev
git clone https://github.com/hoverboardhavoc/hoverboard-firmware.git

To build against a local runtime-hal checkout instead (to change the HAL and the firmware together), clone it beside the firmware and patch that one command, from C:\dev\hoverboard-firmware\motorcontroller in Git Bash:

cargo --config 'patch."https://github.com/hoverboardhavoc/runtime-hal".runtime-hal.path="../../runtime-hal"' image

A patched build rewrites the runtime-hal entry in Cargo.lock; restore it afterwards with git checkout Cargo.lock (the repo's CLAUDE.md, "Running the checks"). runtime-hal keeps its own stable toolchain pin, which never governs this build: rustup resolves the toolchain from the directory cargo runs in, and every firmware build runs in hoverboard-firmware\motorcontroller.

2. Git for Windows, and the line-ending trap

Install Git for Windows. It brings Git Bash, which the repo's tools/*.sh scripts need (they use bash arrays and readlink -f; PowerShell cannot run them).

Do this before cloning. Git for Windows defaults to core.autocrlf=true, and this repo has no .gitattributes, so every shell script would be checked out with CRLF line endings. Git Bash then fails on them with errors like $'\r': command not found, and the failure looks like a broken script rather than a checkout setting.

git config --global core.autocrlf input

If you already cloned with the default, fix it with git config core.autocrlf input then git rm --cached -r . && git reset --hard in each clone.

3. Rust: the pinned nightly and the firmware build

Install

  1. Visual Studio Build Tools 2022 with the "Desktop development with C++" workload (gives the MSVC linker and the Windows SDK). winget install Microsoft.VisualStudio.2022.BuildTools, then select that workload in the installer.
  2. rustup: rustup.rs or winget install Rustlang.Rustup.

Nothing else to pick. motorcontroller\rust-toolchain.toml pins the channel and components, and the first cargo command inside motorcontroller installs exactly that set (shared and tools pin the same nightly; bridge pins 1.92, installed the same way on first use):

channel    = nightly-2026-07-20     (pinned like a version, never bump drive-by)
components = rust-src, rustfmt, clippy
targets    = thumbv7m-none-eabi

The pin is nightly because the shipping image is built with -Z build-std, which is nightly-only and worth 2,408 bytes of flash. The first cargo call in motorcontroller will download the toolchain, which takes a few minutes. Verify with rustc -vV in motorcontroller: it must print the nightly-2026-07-20 commit and your host triple (x86_64-pc-windows-msvc).

Build

motorcontroller\.cargo\config.toml sets [build] target = "thumbv7m-none-eabi", so a bare cargo build there builds for the board. From C:\dev\hoverboard-firmware\motorcontroller, in PowerShell:

cargo build                 # embedded build, default thumbv7m target
cargo image                  # the SHIPPING image (build-std release, the bytes that reach flash)

cargo image is an alias, not a config key, so build-std applies only to that one build. Output: motorcontroller\target\thumbv7m-none-eabi\release\firmware (ELF, with DWARF kept for SWD work).

Tests and the CI gates

A bare cargo test compiles the test binaries for the board and runs none of them, silently. Use the script, from Git Bash:

./tools/host-test.sh                 # what CI's host-test job runs
./tools/host-test.sh -p store        # arguments forward to cargo test

If you would rather stay in PowerShell, that script resolves to this (the motorcontroller suite, then the shared one), and the two are equivalent:

cd motorcontroller; cargo test --target x86_64-pc-windows-msvc -F store/test-fields
cd ..\shared;       cargo test --target x86_64-pc-windows-msvc -F store/test-fields; cd ..

The rest of the Rust gates CI enforces, in PowerShell, with $H as your host triple:

$H = "x86_64-pc-windows-msvc"
cd motorcontroller
cargo fmt --all --check
cargo clippy --target thumbv7m-none-eabi -- -D warnings
cargo clippy --workspace --all-targets --target $H -F store/test-fields -- -D warnings
cd ..\shared
cargo fmt --all --check
cargo clippy --target thumbv7m-none-eabi -- -D warnings
cargo clippy --workspace --all-targets --target $H -F store/test-fields -- -D warnings
cd ..\tools
cargo fmt --all --check
cd ..

Formatting is CI's first gate and runs before anything else, so an unformatted commit fails before the build is even attempted.

4. Making the flashable .bin

CI uses arm-none-eabi-objcopy, -size and -nm from binutils. On Windows the least friction is LLVM's equivalents, which rustup already has the pieces for:

rustup component add llvm-tools
cargo install cargo-binutils
cd motorcontroller
cargo objcopy --release -p firmware --target thumbv7m-none-eabi -- -O binary firmware.bin

The alternative is the Arm GNU Toolchain installer, which gives you the exact arm-none-eabi-* names CI uses, including nm and size for the image-size gates.

Size facts the gates check: code floor 40,000 B (.text plus .hotcode), flashed-span ceiling 59,900 B against a 63,488 B hard limit. If you are only flashing and not developing, skip all of this and download the artifact CI already built: the latest main firmware.zip needs no toolchain at all.

5. The remote app and the Kotlin mirror

Install

  • JDK 17, Temurin, the version CI uses and the level the app compiles to: winget install EclipseAdoptium.Temurin.17.JDK.
  • Android SDK with platform android-35. Android Studio is the easy route (it installs the SDK and lets you add platforms in the SDK Manager). Command-line tools plus sdkmanager --install "platforms;android-35" works too. The app sets compileSdk 35, targetSdk 35, minSdk 26, jvmTarget 17.

Point the build at the SDK, either with an ANDROID_HOME environment variable or by writing apps\remote\local.properties (gitignored):

sdk.dir=C\:\\Users\\<you>\\AppData\\Local\\Android\\Sdk

Gradle itself needs no install. The wrapper fetches Gradle 8.14.

Build and test

From apps\remote:

.\gradlew.bat --console=plain --continue --no-build-cache :app:testDebugUnitTest --rerun :app:testReleaseUnitTest --rerun detekt --rerun
.\gradlew.bat assembleDebug

That first line is CI's remote-app job verbatim. Both variants run the same sources and must report the same non-zero case count; the current suite is 359 cases per variant with 0 detekt findings. The debug APK comes out at apps\remote\app\build\outputs\apk\debug\app-debug.apk.

The wire-protocol mirror is a separate Gradle build. From shared\protocol-kotlin:

.\gradlew.bat test --rerun --no-build-cache --console=plain

Its drift test parses the Rust under shared/ and motorcontroller/ as text and exact-set compares it against the Kotlin, so it needs both repos present but no Rust toolchain.

6. Python tools

Any recent Python 3 (winget install Python.Python.3.12). The scripts import only the standard library, so there is nothing to pip install. They invoke as python3 in CI; on Windows use python:

python tools\check-citations.py        # Kotlin mirror citations resolve to real Rust symbols
python tools\panic-reach.py --selftest # the panic-reachability gate's own parser tests

Citations into specs/ are skipped and the script says so, because specs/ is gitignored. Which brings up the next point.

7. What does not work on Windows, and what is not there at all

ThingState on Windows
specs/ Not in the clone. It is a separate, deliberately local-only git repo, gitignored by the firmware repo, and it stays on the Mac. Nothing in the build needs it; the citation checker skips it.
tools/swd-bridge Expect it not to compile. Its binaries install a SIGINT handler through libc::signal with sighandler_t, which is Unix-only. Use WSL2 or the Mac for the SWD mailbox tools. It is a member of the tools workspace, and nothing else in that workspace links it, so -p selections of the other members still build.
tools/emulator-runner (Unicorn, tier 2) Untried here. It links Unicorn's cmake-built native library, so it needs CMake plus the MSVC build tools (winget install Kitware.CMake) and is built in tools with -p emulator-runner --features unicorn.
tools/flash.sh, tools/bench-lock.sh, the bench Python Bash, and wired to the bench: the Pi runner, the USB probe locations, the bench lock directory. Git Bash can execute them, but the probe side needs OpenOCD plus a WinUSB driver bound with Zadig, and the wireless ESP32 route needs a patched OpenOCD that has no Windows build. Flashing stays on the Mac or the Pi.
